# Stop sending the schema, start skipping the model

The biggest efficiency gain for this qwen2.5:3b config editor comes from not asking the model to read an 8-9 KB JSON Schema at all, and then not calling the model for most requests. The full schema accounts for roughly 2k of the ~2.5k prompt tokens. Nearly all of it restates structure the config instance already shows, and published patch-generation work gets near-full-regeneration accuracy without sending any document schema. Replacing it with a compact per-app path list, or with only the constraints of the fields being edited, cuts cold prefill by about 2.5-4x. Two further changes stack on top. First, make both Ollama calls share one byte-identical, static-first prefix with identical runner options, so llama-server's automatic prefix cache serves almost every request. Second, put the legal paths into the `format` grammar as enums, so invalid-path failures and their retries cannot happen. The most radical lever beats all of these: a regex router plus a slot-filling schema (`field`, `value`, `unit`, `mode`) with deterministic pointer resolution and unit conversion in Python. It removes the app-classification call for literal app names, removes the LLM entirely for the common "set X of service Y to Z" phrasing, and shrinks the remaining LLM prompt to a few hundred cached tokens. None of these gains has been benchmarked for qwen2.5:3b on this task. A 30-100-request labeled eval set, plus per-call logging of Ollama's prompt and cache counters, has to confirm them before the old path is retired.

## The 9 KB schema is mostly distractor, not grounding

The schema can go, because the model needs only two things from it. It needs the exact JSON Pointer paths that exist, and the config instance already lists those. It also needs the handful of constraints on the field being edited: type, enum, min/max and unit. A local measurement of this repo's files shows how lopsided the current prompt is. The minified schemas are **7.5 KB (storefront), 8.9 KB (orders) and 8.0 KB (ledger)**, about 1.9-2.2k tokens at chars/4. A one-line-per-leaf rendering (`path: type (constraints)`) is only **about 2 KB**, and the minified config is **0.9-1.1 KB**. Most of the schemas' bytes are descriptions, defaults and repeated sub-schemas, so a faithful compact rendering is about a quarter of the schema. That is a 3-4x cut. The closest published system, JSON Whisperer (EMNLP 2025 Industry), has a model emit RFC 6902 patches from only the original JSON, the edit request and a short output-format system prompt, with no document schema. It stays **within 5% of full regeneration** accuracy while cutting **output tokens by 31-42%** ([JSON Whisperer](https://arxiv.org/html/2510.04717v1)). Its two characteristic failures were missed related updates and array-index arithmetic errors. Neither is a schema-knowledge problem.

Ollama's docs say "it is ideal to also pass the JSON schema as a string in the prompt" ([Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs)). That advice is about the schema of the *output*, which here is the patch array, not the 9 KB config schema. Sending the config schema actively hurts. Accuracy falls as input grows even when the task stays the same ([Lost in the Middle](https://arxiv.org/abs/2307.03172); [Chroma Context Rot](https://research.trychroma.com/context-rot)), and irrelevant statements cut accuracy by up to 17.9%, with open models hit harder ([arXiv 2504.01201](https://arxiv.org/html/2504.01201v1)). The schemas inline the same probe sub-schema three times (liveness, readiness, startup) and carry 24-26 `default` keys and 60-72 descriptions. Those are exactly the semantically similar distractors that Context Rot flags. Text-to-SQL research reaches the same conclusion: strong models can skip schema pruning ("schema linking"), but for "smaller or prior-generation models … the accuracy gains from schema linking often justify the potential loss" of occasionally pruning a needed element ([The Death of Schema Linking?](https://arxiv.org/abs/2408.07702)). On-device tool selection shows the same pattern. Narrowing the offered tools per prompt cut **execution time by up to 70% and power by up to 40%** while improving success rate on small models ([Less is More](https://arxiv.org/html/2411.15399v1)).

The compact format should be path-keyed lines, not TypeScript. Vendors report that type-definition prompts use 60-85% fewer tokens than JSON Schema ([BoundaryML](https://boundaryml.com/blog/type-definition-prompting-baml); [dspy.rb](https://vicentereig.github.io/dspy.rb/blog/articles/baml-schema-format)), but a patch generator must emit exact pointers. A line such as `/workload/container/resources/memory/limitMiB: integer MiB (min…, max…) = 2048` gives the address, the constraint, the unit and the current value in one place. Nested TypeScript would make a 3B model rebuild the pointer from braces. The data format matters less than its size. Llama 3.2 3B was statistically insensitive to JSON/XML/YAML/Markdown on deeply nested config lookups (52.7% vs 50.7% vs 49.1% vs 48.0%, overlapping CIs), and accuracy was "near 100% with much smaller data amounts" ([Improving Agents](https://www.improvingagents.com/blog/best-nested-data-format)). Flattened `pointer=value` lines cost about 2x the minified JSON on this repo (1.8-2.0 KB, 39-47 lines), so use them only if the path list does not already carry current values. Merging the two, one line per leaf with type, constraint and current value, costs about 0.5-1k tokens per app and replaces both the schema and the config.

Validate-and-retry carries the remaining risk well because the feedback is reliable. Intrinsic self-correction does not reliably help ([Huang et al.](https://arxiv.org/abs/2310.01798)). External execution feedback does ([Self-Debugging](https://arxiv.org/pdf/2304.05128)), and a deterministic JSON Schema validator is the most reliable feedback signal available ([Revisit Self-Debugging](https://arxiv.org/html/2501.12793v1)). The retry message should name the failing pointer, the failing keyword and the allowed range or enum. Then the constraint the model lacked arrives exactly when it is needed. The real recall risk of pruning is optional fields absent from the config, such as a new env var key. A grammar variant that addresses new keys explicitly closes it (see the grammar section below). No published ablation compares instance-only, pruned-schema and full-schema prompts at any model size, so this must be measured locally.

## Prefix caching already exists, and the two-call design probably defeats it

Since **v0.30.0 (May 2026)**, Ollama runs upstream llama.cpp's `llama-server` as its only engine for GGUF models such as qwen2.5:3b ([ollama#16031](https://github.com/ollama/ollama/pull/16031); [v0.30.0](https://github.com/ollama/ollama/releases/tag/v0.30.0)). Every request is sent with a hard-coded `cache_prompt: true`, so llama-server reuses the longest common token prefix in the slot and prefills only the suffix ([llm/llama_server.go](https://github.com/ollama/ollama/blob/main/llm/llama_server.go); [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). For normal models it also leaves llama-server's **8 GiB host-RAM prompt cache** enabled, which can swap an evicted prompt state back in ([llama.cpp PR #16391](https://github.com/ggml-org/llama.cpp/pull/16391)). **v0.30.8** further "improved prompt caching by decoupling it from context shift" ([v0.30.8](https://github.com/ollama/ollama/releases/tag/v0.30.8)). The current release is v0.40.17. Reuse is strictly by prefix: `--cache-reuse` for non-prefix chunks is off and Ollama does not pass it.

Three things in the current design can silently disable caching. The first is option mismatch. The scheduler reloads the model whenever runner options differ (`"runner options changed"`), and those options include `num_ctx`, `num_batch`, `num_gpu` and `num_thread` ([server/sched.go](https://github.com/ollama/ollama/blob/main/server/sched.go)). If the classification call sends a smaller `num_ctx`, or omits it while the edit call sends 16384, every user request triggers **two model reloads** and the cache never survives. This is the single most important thing to check. The second is ordering. Anything variable placed before the schema, such as a request ID, a timestamp or the user text, invalidates everything after it. The layout must be static system prompt, then static per-app schema or path list, then the current config (which changes after each applied edit), then the request. The third is slot contention. With the default `OLLAMA_NUM_PARALLEL=1` there is one slot ([Ollama FAQ](https://docs.ollama.com/faq)), so a classification prompt with a different prefix overwrites the edit prompt's KV on every request. The host cache should restore it, but nobody has published restore-latency numbers. The fixes, cheapest first: drop the classification call (next sections), give it the same leading prefix, or set `OLLAMA_NUM_PARALLEL=2`. The last option doubles KV memory, because Ollama starts llama-server with `-c num_ctx × numParallel`.

The payoff is large because prefill dominates this workload. Measured Qwen2.5-3B prefill is about **347 tok/s at 1k context on a base M2** ([oMLX benchmark](https://omlx.ai/benchmarks/njwmvwmd)). Older llama.cpp 7B tables scale to roughly 400 tok/s pp512 for a 3B model on base M-series chips, and to 2-4x that on Pro/Max ([llama.cpp #4167](https://github.com/ggml-org/llama.cpp/discussions/4167)). Decode for 3B-class models ranges from about 41 tok/s on an M4 mini to 123-335 tok/s on RTX 3060-4090 and 9-24 tok/s on small CPUs ([geerlingguy/ai-benchmarks](https://github.com/geerlingguy/ai-benchmarks)). The table below extrapolates those figures. They are estimates, not measurements of this service.

| Scenario (base M-series GPU, ~350-400 tok/s prefill) | Tokens prefilled | Approx. prefill time |
|---|---|---|
| Today, cold (schema + config + request) | 2,500-3,000 | 6-8 s |
| Today, warm prefix hit on schema only | ~300-600 (config + request) | 1-2 s |
| Compact path list with values, cold | 600-1,000 | 2-3 s |
| Compact path list, warm hit | 50-300 (request) | < 1 s |
| Slot-filling prompt, warm hit | 20-60 (request) | ~0.1 s |

A prefix hit removes about 95% of prefill. Halving the model size only halves it, so caching and shrinking beat model swapping. Verify hits from the responses themselves. Current Ollama reports `prompt_eval_count` as cached plus new tokens and adds a separate `prompt_eval_cached_count` ([llm/llama_server.go](https://github.com/ollama/ollama/blob/main/llm/llama_server.go); [api/types.go](https://github.com/ollama/ollama/blob/main/api/types.go)). One caveat: llama.cpp warns that cached and uncached runs can give non-bit-identical logits ([llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). Temperature 0 therefore does not guarantee identical output across cold and warm requests. Keep validating every patch.

The other runtime knobs are second-order. Flash attention already defaults to auto. `OLLAMA_KV_CACHE_TYPE=q8_0` halves KV memory without speeding prefill, and the docs warn that Qwen2-family models "may be affected more" ([Ollama FAQ](https://docs.ollama.com/faq)). At about 36 KiB per token, 16k context is only ~576 MiB of f16 KV next to ~2 GB of weights, so leave it at f16. Lowering `num_ctx` from 16384 to 8192 or 4096 once prompts shrink saves memory but not time, because prefill scales with prompt length, not allocated context. `num_batch` 1024-2048 can raise GPU prefill throughput, but Ollama reserves an extra 768 MiB-2 GiB of compute memory for it ([llm/llama_server.go](https://github.com/ollama/ollama/blob/main/llm/llama_server.go)). It is worth trying only for cold-path latency, and only if set identically everywhere (or in a Modelfile). Use `keep_alive: -1` plus a warm-up request at startup to prime the prefix.

## Put the legal paths in the grammar, not in the prompt

Ollama passes a `format` JSON Schema to llama-server, which converts it to GBNF, and Ollama keeps a **64-entry LRU of converted grammars** keyed by schema text ([llm/llama_server.go](https://github.com/ollama/ollama/blob/main/llm/llama_server.go)). A byte-identical per-app schema therefore pays the conversion cost once. llama.cpp's converter compiles `enum` into a flat alternation of literals and `anyOf` into a union ([json-schema-to-grammar.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/json-schema-to-grammar.cpp)). That makes `"path": {"enum": [...all ~40-50 valid pointers...]}` expressible, and an invalid-path patch impossible. There is no documented size limit. There is also no trie merging, and llama.cpp's grammar engine benchmarks slower than XGrammar-class engines on per-token masking ([XGrammar](https://arxiv.org/abs/2411.15100)). Every pointer shares a long `"/workload/container/...` prefix, so all alternatives stay alive in parallel until they diverge. Use **short semantic aliases** in the enum (`storefront.memory_limit`, `storefront.cpu_limit`) and map them back to pointers in Python. That cuts output tokens, grammar ambiguity and `~1`-escaping risk in one move. Practitioner reports of grammar overhead range from 10-80% slower generation to faster end-to-end runs ([insiderllm](https://insiderllm.com/guides/structured-output-local-llms/); [khimananda](https://khimananda.com/blog/structured-outputs-and-json-mode-from-llms); [DEV](https://dev.to/jangwook_kim_e31e7291ad98/ollama-structured-outputs-in-practice-getting-type-safe-json-from-local-llms-with-pydantic-m38)). None isolates enum size, and for a 50-200-token reply after a multi-thousand-token prefill the overhead is small either way.

Per-value typing works best grouped by type, not per path. The converter's documented limits shape the design: no mixing of `properties` with `anyOf`/`oneOf` in one node, `minimum`/`maximum` enforced only for `integer`, `patternProperties` unsupported, `pattern` only when anchored, and **unsupported keywords skipped silently** ([llama.cpp grammars README](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)). A string `pattern` nested inside array `items` has also produced HTTP 400 "failed to parse grammar" and, in single-slot setups, taken the server down ([llama.cpp #25895](https://github.com/ggml-org/llama.cpp/issues/25895)). The robust shape is an `items` that is itself an `anyOf` of three to five complete objects: integer-valued paths with an integer `value`, string-valued paths with a string `value`, boolean paths, and an `add_key` variant. Declare `path` before `value` and mark both required. The `add_key` variant is `{"op":"add_key","parent": enum[map-typed paths such as …/envs], "key": {"pattern":"^[A-Z_][A-Z0-9_]*$"}, "value": string}`, and Python builds and escapes the pointer. Keep patterns off `path` entirely, or the enum guarantee collapses into "any string". Avoid per-path `const` branches: about 100 near-identical union alternatives recreate the parser-stack blow-up that once slowed llama.cpp sampling badly ([llama.cpp PR #6616](https://github.com/ggerganov/llama.cpp/pull/6616)). Run each generated `format` schema once at startup with a tiny request, so grammar failures surface at boot. Set `num_predict` to about 256 rather than thousands. An Ollama MLX-engine bug made `format` output emit whitespace until `num_predict` ([ollama#18567](https://github.com/ollama/ollama/issues/18567)), and a cap bounds the damage from any runaway generation.

## Most requests need neither the classifier nor the patch generator

The example traffic ("set ledger service memory to 1024mb", "set TENANT env to globex for orders service", "lower cpu limit of storefront service to 80%") is slot-filling, not open-ended editing. The cheapest robust decomposition moves path resolution and unit arithmetic out of the model. Python or, failing that, the LLM fills a tiny fixed schema `{app, field: enum[~10-20 semantic kinds], key?, value, unit: enum[MiB, GiB, MB, m, %, cores, …], mode: enum[set, increase, decrease, add, remove]}`. Python then maps `(app, field)` to a pointer and converts units. This prompt needs neither the schema nor the config, so it is a few hundred static, fully cacheable tokens, and its grammar is a handful of small enums. Practitioner guidance on local structured output points the same way: flatten schemas, drop optional fields, and split large extractions into focused calls, because every optional field enlarges both the grammar and the model's decision space ([Liquid AI docs](https://docs.liquid.ai/deployment/on-device/llama-cpp/structured-output); [khimananda](https://khimananda.com/blog/structured-outputs-and-json-mode-from-llms)). Native `tools` calling is a worse channel for small local models. Google's kubectl-ai needs a `--enable-tool-use-shim` because some local models "require special prompting to enable tool calling" ([kubectl-ai](https://github.com/GoogleCloudPlatform/kubectl-ai)).

Deterministic routing comes before any of this. If exactly one of `storefront`, `ledger` or `orders` appears as a whole word outside the value span, call 1 is unnecessary. If none or several appear, fall back to the classifier. Matching outside the value span matters because an env value like `storefront-lobby` contains an app name. A keyword table (memory|mem|ram, cpu, env|environment variable, replicas) plus a number-and-unit regex covers the example phrasing and can emit the slot object directly, with zero LLM calls. Anything with unmatched content words, multiple numbers or multiple fields escalates to the LLM slot filler, and from there to the full patch path. This rules-first, LLM-fallback cascade is well established ([octoroute](https://docs.rs/crate/octoroute/latest/source/src/router/hybrid.rs); [FrugalGPT](https://arxiv.org/abs/2305.05176)). FrugalGPT's lesson is that escalation needs a verifier, and here the full-schema validator plus apply-and-diff is that verifier for rule output and LLM output alike. Python must also pin down the semantic ambiguity a 3B model will guess at inconsistently. The repo's current prompt defines "80%" as 80% of the current limit ("80% of 1500 = 1200"), which is a different operation from "80% of a core". Encode that rule in code, not in prose for the model.

Cache exactly, never semantically. An exact cache keyed on (normalized request, app, config hash) is safe and nearly free. Semantic caches have documented false-hit problems: GPTCache produced **54 false hits vs 3** for MeanCache on queries that should all have missed ([MeanCache](https://arxiv.org/pdf/2403.02694)), and it matched semantically unrelated queries ([arXiv 2401.08138](https://arxiv.org/pdf/2401.08138)). In a config editor, "increase" vs "decrease" or 512 vs 1024 embed almost identically, so a false hit silently applies the wrong change.

Model choice is the weakest lever. No benchmark compares qwen2.5:0.5b/1.5b/3b, qwen3:1.7b/4b, llama3.2 or gemma3 on picking a JSON path and value. Indirect evidence says 1B-class models are "too small to maintain constraints effectively" ([OMNIX](https://huggingface.co/datasets/LemOneLabs/OMNIX_Benchmarks_Latest)), and 1.5B extraction models needed fine-tuning to be reliable ([arXiv 2607.21284](https://arxiv.org/pdf/2607.21284)). Grammars guarantee syntax, not correct choices. Keep qwen2.5:3b, which Qwen markets for structured-data understanding and JSON output ([model card](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct)). Once the slot schema exists, test qwen2.5:1.5b on it, and qwen3:4b with `think: false` on the fallback patch path. Without `think: false`, qwen3 burns tokens on reasoning.

## Prioritized recommendations for this service

Gains below are inferences from the evidence above, not measurements. Effort assumes the existing Python/FastAPI service.

| # | Change | Expected gain | Effort | Risk |
|---|---|---|---|---|
| 1 | Send identical `options` (same `num_ctx`, nothing else varying) and model tag on every call. Order the prompt static system, then static per-app block, then config, then request. Serialize deterministically. Run Ollama ≥ 0.30.8, `keep_alive: -1`, warm-up at boot. Log `prompt_eval_count`, `prompt_eval_cached_count`, `prompt_eval_duration`, `eval_duration`. | Removes possible double reloads. Warm prefill drops from ~2.5k to ~0.3-0.6k tokens with no accuracy change | Hours | Low |
| 2 | Regex app router that skips the classification call when exactly one app name appears outside values, with LLM fallback | One fewer LLM call on most requests, and no slot eviction | ~20 lines | Low |
| 3 | Exact-match result cache on (normalized request, app, config hash) | Repeat requests cost zero | ~10 lines | Low |
| 4 | Replace the full JSON Schema in the prompt with one line per leaf: pointer or alias, type, unit, bounds/enum, current value. Drop the separate config. Keep full-schema validation locally, and put the exact failing pointer, keyword and allowed values into the retry. | Cold prompt ~2.5k down to ~0.6-1k tokens (2.5-4x prefill). Likely equal or better accuracy | ~1 day (schema walker must handle `anyOf`/`allOf`/`patternProperties`) | Medium: absent optional fields, mitigated by #5's `add_key` and validator retries |
| 5 | Grammar-constrained output: `items` as `anyOf` of 3-5 typed op shapes, alias `path` enums per app, `add_key` with an anchored key pattern, `num_predict` ≈ 256. Startup self-test of each schema. | No invalid-path or unparseable outputs, so fewer retries. Shorter outputs | ~1 day | Medium: grammar parse bugs and per-token overhead, caught by the self-test and the benchmark |
| 6 | Slot-filling fast path: deterministic regex slots first, then LLM slot filler with the tiny schema. Python resolves pointer, units and relative math, then validates. Current patch path becomes the fallback. | Zero LLM calls for common phrasing. Otherwise a few hundred cached tokens and ~30 output tokens | 2-3 days | Medium: coverage gaps, handled by escalation |
| 7 | Runtime tuning: `num_batch` 1024/2048 on GPU only. Shrink `num_ctx` to 4096-8192 after #4/#6 (memory only). Leave flash attention on auto and KV at f16. | Modest cold-path speedup and memory headroom | Minutes | Low, if set identically everywhere |
| 8 | Model trials: qwen2.5:1.5b for the slot filler, qwen3:4b `think:false` for the fallback | Uncertain: up to 2x faster for 1.5b | Hours, given the eval set | Medium to high without the eval |

Items 1-3 are free wins to ship immediately. Item 6 is the structural endgame. Once it lands, items 4 and 5 matter mainly for the fallback path, so one reasonable sequence is 1-3, then 6 with 5's grammar techniques, then 4 to harden the fallback.

## What to measure locally before trusting any of this

The first measurement is the eval set itself. Take 30-100 requests (the showcase and integration cases plus paraphrases, relative edits, env additions, ambiguous app mentions and multi-field requests), each labeled with the expected post-apply config, not the expected patch text. Score every variant on post-apply equality, first-try validator pass rate, retries per request and end-to-end latency. Run four prompt ablations on qwen2.5:3b: full schema, compact path list, path list plus candidate constraints only, and slot schema. That settles whether the schema helps or hurts this model, which no paper has measured. For caching, compare cold and warm requests, log `prompt_eval_cached_count` against prefix length, and test alternating classify and edit calls with `OLLAMA_NUM_PARALLEL=1` against `=2`. Model reloads show up as `load_duration` spikes and in `ollama ps`. For grammars, measure `eval_count/eval_duration` with no `format`, the loose patch schema, and alias enums of 10, 100 and 300 values, because no one has published enum-cardinality overhead for llama.cpp. On the target box, run `llama-bench -p 512,2048,8192 -n 128` to replace the extrapolated prefill table with real numbers, and measure what fraction of real requests the regex fast path resolves correctly.

## Conclusion

This service's cost is set by the prompt design, not by the model. The runtime already caches prefixes, the grammar engine already accepts path enums, and the validator is already a perfect feedback oracle. What wastes them is a prompt that leads with a large, distractor-heavy schema, a second call that likely evicts the first one's cache, and an output format that makes the model rebuild pointers it could have picked from a list. Recast the problem as "identify a field and a number" and the efficient design follows: Python handles addressing, units and arithmetic, the grammar enforces legal choices, and the 3B model is left with the only part that needs language understanding, the long tail of phrasings.

The same move improves correctness, not just speed. Every token removed from the prompt also removes a distractor for a small model, and every decision moved into code becomes deterministic and testable. Treat any remaining LLM call as a fallback whose rate is a metric to drive down, rather than the default path to optimize.
